# 单词表文档解析评测

> 这是 `words` 的一个子项目：把「从 Word/PDF 里提取单词」这件事，从「感觉能用」变成「有数字」。
> 目的是给作品提供一个可复现、可对比的评测基准，而不是靠主观描述。

## 一、为什么做

所有背单词软件都说「支持导入自定义词库」，**但没有一家公布解析准确率**。

原因不难猜：这事做不好。中文单词表文档的排版千奇百怪——

- 一行一个词条 / 一个词条占三行
- Word 表格 2～5 列，列序不固定
- 音标在斜杠里、方括号里、或者干脆没有
- 中文释义跨行、带括号注释、带例句
- 页眉页码混在正文里

所以第一步不是改算法，是**把「准不准」量出来**。

## 二、测试集

`testset/` 下每份文档配一个 `.expected.json`（人工标注的正确答案）。

| 文件 | 格式特征 | 词条数 |
|---|---|---|
| `01_一行一个.txt` | 最规整：`单词 词性 中文` | 20 |
| `02_单词释义分行.txt` | 单词一行、释义下一行（需要跨行合并） | 20 |
| `03_带序号星号.txt` | 行首编号 + 单词带 `*` | 20 |
| `04_带音标斜杠.txt` | `/əˈbændən/` 形式音标 | 20 |
| `05_方括号音标.txt` | `[əˈbændən]` 形式音标，无词性 | 20 |
| `06_表格四列.docx` | Word 表格：单词 / 音标 / 词性 / 中文 | 20 |
| `07_一行多词性.txt` | `abstract n. 摘要 adj. 抽象的` | 10 |
| `08_脏文档带页码.txt` | 正文里混了标题、页码、说明文字 | 12 |

**说明**：这 8 份是「真实单词 + 构造排版」，用来把工具链跑通。
真实文档（从群里收的、网上下载的）会放进来后，准确率一定会掉——这正是要测的东西。

## 三、指标

| 指标 | 定义 |
|---|---|
| **召回率** | 解析出的词条中，拼写能对上标注的有多少 / 标注总数 |
| **词性正确率** | 召回的词条里，词性跟标注一致的比例 |
| **释义正确率** | 召回的词条里，中文释义包含标注内容的比例 |
| **多出** | 解析出但不在标注里的条目数（误收，比如把页眉当词条） |

三项都是「越高越好」，多出是「越少越好」。

## 五、这个 100% 说明什么

**说明常见格式已经处理干净了**，但不说明整个问题解决了。

真正的难点不在这些格式上，而在：

1. **PDF 双栏排版**——同一 y 坐标上有两列内容，按行拼接会把左右两栏混在一起；
2. **表格合并单元格**——跨行跨列的单元格会让列映射错位；
3. **音标与释义跨行**——一个词条的音标在上行、中文在下行、词性在中间；
4. **例句混排**——英文例句行可能被误判成词条；
5. **扫描版 PDF**——没有文字层，直接无解。

这些在 txt 里表达不出来，必须用真实 PDF 测。

## 七、怎么复现

```bash
cd tools
node eval.mjs
```

会输出上面的表格，并把明细（每份文档漏了哪些词、多收了哪些词）写进 `tools/eval-report.json`。

依赖：Node 18+（用到 `File` 和 `DecompressionStream`）。docx 解析在 Node 里靠 `tools/minidom.mjs` 模拟 `DOMParser`。
